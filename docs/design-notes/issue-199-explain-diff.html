Background

The card draws the solar system as a flat, top-down diagram: the Sun sits at the centre of the SVG, every other body is a small <circle> placed on its orbit ring. Until this change a planet was just a filled disc — a coloured dot. Issue #199 asks for two things on top of that: bodies that read as round (a little 3-D), and a day / night shading that shows which side faces the Sun. Plus a soft glow behind the Sun and a nudge of the planet palette toward real-world colours.

Two design constraints shaped everything. First, the card re-builds its whole SVG imperatively on every date change — there is no virtual DOM diffing planets — so anything expensive per body is paid on every redraw. Second, the tests run in jsdom, which has no <canvas> and no real layout: a test can inspect the SVG element tree but cannot rasterise it. Any rendering trick has to survive both.

The feature is split into two independent switches in the card config, modelled as ShadeOptions { sphere: boolean; dayNight: boolean }:

  • display: 2d | 3d → sphere — flat disc vs. a body that looks like a ball.
  • shading: true | false → dayNight — whether the Sun-facing / anti-Sun split is drawn.

Keeping them orthogonal matters: an earlier attempt folded both into one three-value enum (none | flat | sphere) and immediately regretted it — you could no longer ask for a flat disc with day/night, or a round ball without it.

A recurring theme: the light direction for any body is free. The Sun is always at the SVG centre (CENTER, CENTER), so the vector from a body at (x, y) toward the light is just (CENTER - x, CENTER - y) — a screen-space delta between two already-placed points. It is not an orbital angle, so it does not pass through the ±1 ecliptic-mirror (polarOffset) that every orbital angle must (see the repo's #94). sunBearing(x, y) returns that angle in degrees, or null when the body is the Sun.

The idea

Day / night: an elliptical terminator

The shaded side of a body is drawn as one translucent dark shape over the anti-Sun half. The boundary between lit and dark — the terminator — started as a straight diameter, which read as a hard slice through a coin rather than the curve of a sphere. terminatorShadowPath(x, y, r, bow) replaces the straight edge with an elliptical arc: from one pole, a semicircle around the dark limb to the other pole, then an arc back whose minor radius is bow · r, bowed into the dark side so the lit hemisphere reads as bulging toward you. bow = 0.22.

Getting the arc's direction right was subtle. A second A command in an SVG path starts where the previous command ended, not at the M point — so a bulge-direction heuristic copied from a single-arc helper computed the wrong sign, and a test agreed with it. The real arc was bowing toward the Sun (shrinking the lit side) while the reconstruction said otherwise. Only sampling the arc with the actual SVG endpoint-to-centre parameterisation caught it. Lesson: for multi-command path geometry, assert against a real parameterisation or a rendered snapshot, never a bespoke heuristic.

3-D: why a gradient never worked

A circle only looks like a sphere because of how light falls across it — a bright-to-dark gradient. The obvious move is an SVG <radialGradient> overlay, and it was tried about ten ways over as many rounds:

AttemptWhy it failed
Bright centre spotThe eye assumes light comes from above — a centred highlight reads as "lit from the top".
Highlight offset toward the Sun, carried by a per-body rotate() groupThe rotation was exact to 0.00°, but every stop-value tune read as either a hot spot or a flat wash.
Limb darkening only (dark rim, flat centre)Too weak reads as flat; strong enough to see reads as a blurry vignette, and the disc looked ~6% small because the soft edge stopped short.
Opaque radial fill in the body's own hueStill reads as "lit from somewhere".

The conclusion: a translucent radial cannot give volume without also implying a light source and a direction. "Looks round" and "looks lit" are not separable with a gradient.

3-D: bake the sphere

So instead of computing a fake sphere at render time, pre-compute a real one, once, off-line. scripts/gen-sphere-sprites.mjs is a standalone Node script (with its own ~40-line PNG encoder — no dependencies) that evaluates a Lambert lighting model per pixel over a 128×128 disc and writes a grayscale-plus-alpha PNG. It produces two:

SPRITE_SOFT
light toward viewer,
ambient 0.34
→
shading OFF:
pure volume,
no direction
SPRITE_LIT
light in the plane,
ambient 0.28,
tight terminator
→
shading ON:
rotate toward Sun —
the sprite IS
the day/night

Both PNGs are inlined into bodies.ts as data: URIs (~13 KB total). At render time the body is a plain <image href=SPRITE_*>. To colour it, a one-line <feColorMatrix> filter per distinct hue multiplies the grayscale by the planet's RGB. When shading is on, the lit sprite gets transform="rotate(sunBearing(x,y))" so its bright half faces the Sun — the sprite carries the terminator, so no separate shadow shape is drawn for 3-D bodies. The Sun itself opts out entirely: it is a light source, drawn as a flat disc, its depth coming from the halo.

Nothing rasterises at runtime, so jsdom is happy; the light parameters live in a re-runnable script, not in guessed hex stops; and 2d and 3d dark sides are reconciled by a shared shadeFill() = color-mix(in srgb, colour 28%, black), so a shadowed planet is colour × 0.28 in either mode.

The code

Everything lives in src/renderer/. The renderer entry point renderSolarSystem() (index.ts) walks the bodies and calls, per body, one of:

  • renderBody(svg, x, y, body, showLabel, shade) — planets and the Moon.
  • renderSaturn(svg, x, y, body, shade) — core disc plus two ring circles.
  • renderCometBody(svg, x, y, comet, sunX, sunY, tail, shade) — head plus tail.

bodies.ts

// display: 3d -> a pre-baked Lambert sprite, tinted per colour.
export function renderSphereSprite(svg, x, y, r, color, sunDeg /* number | null */) {
  // one <filter id="tint-<hex>"> per distinct colour: a feColorMatrix that
  // multiplies the grayscale sprite by (R, G, B)
  ensureTintFilter(svg, color);
  const attrs = { href: sunDeg === null ? SPRITE_SOFT : SPRITE_LIT,
                  x: x - r, y: y - r, width: 2 * r, height: 2 * r,
                  filter: `url(#tint-${slug(color)})` };
  if (sunDeg !== null) attrs.transform = `rotate(${sunDeg} ${x} ${y})`;
  svg.appendChild(createSvgElement("image", attrs));
}

export function sunBearing(x, y) {
  if (x === CENTER && y === CENTER) return null;        // the Sun
  return (Math.atan2(CENTER - y, CENTER - x) * 180) / Math.PI;
}

// shared: the night-side tone, matched between 2d and 3d.
const shadeFill = (color) => color
  ? { fill: `color-mix(in srgb, ${color} 28%, black)`, "fill-opacity": 0.92 }
  : { fill: SHADOW_FILL, "fill-opacity": SHADOW_OPACITY };  // #05070c fallback

renderBody then branches: shade.sphere && !atCenter → the sprite (rotated iff shade.dayNight); otherwise a flat <circle>, and if shade.dayNight a renderBodyShadow wash on top. The Sun (atCenter) is always the flat circle.

svg-utils.ts

// The dark region's outline: pole -> semicircle round the dark limb -> pole,
// then an elliptical arc back, bowed into the dark side (sweep flag 0).
export function terminatorShadowPath(x, y, r, bow, lightFrom = { x: CENTER, y: CENTER }) {
  const dx = lightFrom.x - x, dy = lightFrom.y - y;
  if (Math.hypot(dx, dy) < 1e-9) return null;            // body at the light
  const phi = Math.atan2(dy, dx);
  const p1 = pole(x, y, r, phi + Math.PI / 2);
  const p2 = pole(x, y, r, phi - Math.PI / 2);
  return `M ${p1.x} ${p1.y} A ${r} ${r} 0 0 1 ${p2.x} ${p2.y}` +
         ` A ${bow * r} ${r} ${deg(phi)} 0 0 ${p1.x} ${p1.y} Z`;
}

renderBodyShadow (2d day/night + Saturn's band)

Signature renderBodyShadow(svg, x, y, coreR, reach = coreR, coreShaded = false, shadeColor?). The lone-body path uses shadeFill(shadeColor). For Saturn (reach > coreR) it also builds a <clipPath id="saturn-shadow"> holding a rotated rect the width of the core, and a <mask id="saturn-core-cut"> that punches the core out — so the band darkens only the rings and the gap, once, in the same shadeFill tone as the core. When coreShaded (i.e. the 3-D sprite already carries the core's terminator) the core wash is skipped and only the band is drawn.

Tests

Changing how a body is drawn moves the entire test-locator surface. Roughly 40 assertions across bodies / comets / index / solar-view tests were rewritten: image[filter="url(#tint-<hex>)"] now stands in for circle[fill="#hex"] wherever a 3-D body is expected, routed through one bodyCircle / bodyPos / sphere3dCount resolver in index.test.ts. The coarse full-scene snapshot was regenerated. Coverage stays at 100%.
