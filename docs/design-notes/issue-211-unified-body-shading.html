Issue #211 · Design note

One shading path for 2D and 3D

approved

display: 3d with shading: true currently swaps in a second sprite, SPRITE_LIT, rotated toward the Sun. Its hard hemisphere split reads flatter than the plain round ball. Drop the swap: always draw the round SPRITE_SOFT, and give 3D the same day/night overlay 2D already uses.

#211 2026-09-02 supersedes part of #199 2 slices

Problem

#199 baked two 128 px Lambert sphere sprites (note): SPRITE_SOFT (viewer-weighted light, high ambient — a round ball with no direction) and SPRITE_LIT (in-plane light, tight terminator). renderBody picks between them: 

if (shade.sphere && !atCenter) {
  renderSphereSprite(svg, x, y, body.size, body.color, shade.dayNight ? sunBearing(x, y) : null);
} else {
  svg.appendChild(createSvgElement("circle", { cx: x, cy: y, r: body.size, fill: body.color }));
  if (shade.dayNight && !atCenter) renderBodyShadow(svg, x, y, body.size, body.size, false, body.color);
}

With shading on, the 3D body is SPRITE_LIT rotated by sunBearing. The lit/dark split is a hard edge across the disc; against the softly-lit unshaded ball it looks less three-dimensional, not more. Meanwhile the 2D branch already has a gentler day/night treatment — renderBodyShadow → terminatorShadowPath (an elliptical wash that bows 0.22·r into the dark side) filled by shadeFill (color-mix(colour 28%, black)). Two treatments for one concept.

Approach — designed twice

A. Grow the 3D branch

Keep the if / else shape. In the shade.sphere branch, call renderSphereSprite(…, null) unconditionally (always SPRITE_SOFT) and add the same if (shade.dayNight) renderBodyShadow(…) line the else branch has. Minimal diff, but the day/night call is now written twice, once per branch, and has to be kept in sync by hand — the exact split-treatment shape that caused the problem.

B. Collapse to form + overlay ← chosen

After the change both modes do the same two steps: draw the body form, then if dayNight, wash the night side. Only the first step differs. Write it that way: 

  const atCenter = x === CENTER && y === CENTER;
- if (shade.sphere && !atCenter) {
-   renderSphereSprite(svg, x, y, body.size, body.color, shade.dayNight ? sunBearing(x, y) : null);
- } else {
-   svg.appendChild(createSvgElement("circle", { cx: x, cy: y, r: body.size, fill: body.color }));
-   if (shade.dayNight && !atCenter) renderBodyShadow(svg, x, y, body.size, body.size, false, body.color);
- }
+ if (shade.sphere && !atCenter) {
+   renderSphereSprite(svg, x, y, body.size, body.color);
+ } else {
+   svg.appendChild(createSvgElement("circle", { cx: x, cy: y, r: body.size, fill: body.color }));
+ }
+ if (shade.dayNight && !atCenter) renderBodyShadow(svg, x, y, body.size, body.size, body.color);

renderSphereSprite loses its sunDeg parameter entirely; renderBodyShadow loses coreShaded (see slice 2). renderSaturn and the comet head (renderCometBody) get the same shape: sprite-or-circle, then one renderBodyShadow call gated on dayNight. Saturn's call keeps its reach argument (SATURN_RING_OUTER_RADIUS) so the ring band still draws.

B. The duplicated day/night call in A is exactly the "two treatments for one concept" this issue removes — leaving it duplicated in the code just moves the seam. B makes 2D and 3D share the literal call site, so they cannot drift.

Design invariant preserved

Bodies still read as spheres (SPRITE_SOFT is the same ball display: 3d + shading: false already shows). The dark side stays a dark shade of the body's own hue via the shared shadeFill, never black. The display / shading switches remain two independent booleans (ShadeOptions { sphere, dayNight }).

LESSONS.md. This reverses one #199 decision only — "the lit sprite's terminator is the day/night for 3d, no separate wash" (line 24). It does not revive the abandoned #sphere-3d gradient: volume still comes from the baked sprite, so "bake the sphere" (line 9) and "don't revive the gradient" (line 72) still hold. The enum guardrail (line 46, two independent booleans) is untouched.
