Background

The card renders the solar system into one SVG element, and it never redraws that SVG to zoom. Zooming is a viewBox swap: the SVG keeps all its coordinates, and the browser just decides how much of that coordinate space to fit on screen. A smaller viewBox width shows less of the scene, larger, so it reads as zoomed in.

There is a fixed ladder of four zoom rungs, defined in src/card/zoom-levels.ts as the viewBox width each one shows:

rung1234
width800640480320

The rungs are evenly spaced — 160 units apart — so stepping between two adjacent rungs is always the same visual distance. ZoomController owns which rung is current and animates the transition; ZoomAnimator is a tiny helper that eases a single number (the width) from one value to another over a fixed 2 s, one requestAnimationFrame at a time.

Two config options drive an unattended slideshow of the zoom. periodic_zoom_change (on by default) tells the card to step the zoom once on every 60 s refresh tick, until you touch the view yourself. periodic_zoom_max (default 4) is how far in it is allowed to go. default_zoom (default 1) is where the view starts and where the Now button returns it.

What was wrong. The cycle walked 1 → 2 → 3 → 4 and then, on the next tick, snapped straight back to rung 1. That snap is a single 2 s tween covering three rungs at once (width 320 → 800, 480 units) — so the reverse leg runs at three times the on-screen speed of every forward step, in the opposite direction. It is the one jarring moment in an otherwise calm drift. And it always returns to a hard-coded rung 1, never to default_zoom: once the cycle takes the first step, the configured resting level is abandoned until you press Now.

Separately, the tween used a cubic ease-in-out. Cubic in/out barely moves for the first quarter of its duration, then accelerates hard through the middle and brakes hard at the end — a pronounced velocity spike. On a slow ambient move that reads as a lurch rather than a glide.

The idea

Instead of wrapping, bounce. When the cycle reaches an end of its travel, it turns around and walks back the way it came. Every step is then exactly one rung — one even 160-unit move — whether the cycle is heading in or heading out. There is no longer a special three-rung leg to run fast.

The two ends of the bounce are the two config values that already exist: default_zoom is the near end, periodic_zoom_max is the far end. With the defaults that is:

A useful side effect: the cycle now passes back through default_zoom on every inward swing, which the old wrap never did once it left.

Driving it from the real position, not a counter

The tempting way to write a ping-pong is a step counter fed through a triangle wave — level = f(tick_count, near, far). That would be a bug here. The two ends are live config: someone can edit periodic_zoom_max in the Lovelace editor while the cycle is running. A counter has no idea where the view actually sits, so if the max drops from 4 to 2 while the cycle is parked at rung 4, the next f(…) could jump the view several rungs at once — recreating exactly the lurch this change removes.

So the controller keeps a one-bit direction, _periodicDirection (+1 out, -1 in), and each tick moves ±1 from wherever the zoom currently is, flipping the direction first if that step would carry it past an end. Whatever state the level is in when the tick fires — stranded past the max by a config edit, left mid-ladder before Now — the next move is always a single rung, and the cycle self-corrects back into range without a jump.

at rung 3, heading out→ 4, then flips to heading in

And a gentler curve

The tween swaps its cubic ease for a sine ease-in-out. The two curves agree exactly at the start, the midpoint and the end; in between, sine is the gentlest standard in/out shape — it leaves the mark smoothly and settles onto the target smoothly, with no mid-move speed-up. At a quarter of the way through a rung, cubic has covered 6.25% of the distance and is about to lunge; sine has covered 14.6% and is already coasting. Same 2 s duration, same endpoints.

The code

Two source files, one small commit each.

src/card/zoom-controller.ts — the ping-pong

A new field private _periodicDirection: 1 | -1, initialised to 1 in the constructor. advancePeriodic() — the method the 60 s tick calls — is rewritten:

const near = this._defaultZoomLevel;
const far = this._periodicZoomMax;
if (near >= far) return;              // ends coincide: hold still
let dir = this._periodicDirection;
if (this._zoomLevel + dir > far) dir = -1;
else if (this._zoomLevel + dir < near) dir = 1;
this._periodicDirection = dir;
this._setZoomLevel(this._zoomLevel + dir);

The old body was a single line: const next = this._zoomLevel >= this._periodicZoomMax ? MIN_ZOOM : this._zoomLevel + 1. The near >= far guard returns before any side effect — no animation, no re-render — so a misconfigured card that sets default_zoom to the max simply sits still instead of eating a spurious tween every minute. _setZoomLevel still clamps its argument to the 1–4 ladder, so a redundant as ZoomLevel cast on the old line was dropped by the review's /simplify pass.

resetToDefault() (the Now button) gains one line, this._periodicDirection = 1, so a resumed cycle heads outward from default_zoom. This line is belt-and-braces: if it were missing, the flip rule would still set dir = 1 on the next tick, because the view is sitting at near and near - 1 < near. It is kept as an explicit statement of the intended invariant.

src/card/zoom-animator.ts — the curve

The private helper easeInOutCubic(t) becomes easeInOutSine(t), body -(Math.cos(Math.PI * t) - 1) / 2, and the one call site inside animateTo's frame step is updated. ZOOM_ANIMATE_DURATION_MS stays 2000. Nothing else in the animator changes — it still tweens one number over a fixed duration, frame by frame.

Tests

In zoom-controller.test.ts, the test that pinned the old wrap now asserts the full ping-pong sequence [2, 3, 2, 1, 2, 3] from six advancePeriodic() calls, and a new test drives the config-edit-strands-the-level case — the one that distinguishes this design from a counter-based one. Three card-level tests in card.auto-zoom.test.ts that asserted the → 1 snap were migrated to the turnaround behaviour and the near ≥ far hold. zoom-animator.test.ts gains one assertion: at a quarter of the tween the eased width is past where cubic would leave it. Coverage stays at 100%.
