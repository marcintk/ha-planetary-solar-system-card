Issue #222 · Design note

Ping-pong the zoom auto-cycle

approved

The periodic zoom cycle steps one rung a minute to periodic_zoom_max, then snaps straight back to level 1 — one 2 s tween covering three ladder rungs at ~3× the speed of every other step, and it never revisits default_zoom again. Make it a ping-pong that turns around at each end, and swap the easing curve for one that doesn’t lurch.

#222 2026-09-07 2 slices

Problem

The auto-cycle lives in ZoomController.advancePeriodic() (src/card/zoom-controller.ts). The card’s 60 s refresh timer (_refreshMs, src/card/card.ts) calls _zoom.tick(), which calls it while the cycle is on and the user hasn’t taken the camera: 

advancePeriodic(): void {
  if (!this._initialized) return;
  const fromWidth = this._size;
  // 1 → 2 → 3 → 4, then hard reset to 1
  const next = this._zoomLevel >= this._periodicZoomMax ? MIN_ZOOM : this._zoomLevel + 1;
  this._setZoomLevel(next as ZoomLevel);
  this._apply(fromWidth);
}

_apply() hands the width change to ZoomAnimator.animateTo(), which tweens the on-screen viewBox width over ZOOM_ANIMATE_DURATION_MS = 2000 with easeInOutCubic. Two things read as unnatural:

  • The snap-back. Every forward step moves one ladder rung (widths 800 → 640 → 480 → 320, an even 160 units each) in 2 s. The 4 → 1 reset moves three rungs (320 → 800, 480 units) in the same 2 s — a lurching zoom-out at triple the speed of everything around it. And it abandons default_zoom permanently after the very first step: the cycle only ever bounces off hard-coded level 1, never the level the card was configured to rest at.
  • The curve. easeInOutCubic (t<.5 ? 4t³ : 1-(-2t+2)³/2) has a steep mid-move velocity spike — it accelerates hard out of rest and brakes hard into the target. On a slow ambient drift that reads as a shove, not a glide.

The change

Bounce between two endpoints instead of wrapping:

  • Near endpoint = default_zoom (the controller already holds it as _defaultZoomLevel). The cycle now passes back through the configured rest level on every inward swing — the thing it never did before.
  • Far endpoint = periodic_zoom_max, unchanged meaning, no longer a wrap point.
  • Default config (default_zoom: 1, periodic_zoom_max: 4): 1 2 3 4 3 2 1 2 3 4 …
  • Every step is exactly one rung, so the 2 s tween is now a uniform visual speed in both directions.

And in zoom-animator.ts, easeInOutCubic → easeInOutSine (-(cos(πt)-1)/2) — the gentlest standard in/out curve, no velocity spike. Duration stays 2000; the rAF frame loop is untouched (it already renders at the display’s native rate, so “frames” needs no change). The 60 s cadence and the uniform one-tick dwell on every rung are unchanged.

Approach — designed twice

A. Stored direction on the controller ← chosen

Add _periodicDirection: 1 | -1 (init 1 = outward). Each tick, move one rung the way we’re going; if that would overshoot an endpoint, flip first: 

advancePeriodic(): void {
  if (!this._initialized) return;
  const near = this._defaultZoomLevel;
  const far = this._periodicZoomMax;
  if (near >= far) return;                       // no room to cycle — hold still
  const fromWidth = this._size;
  let dir = this._periodicDirection;
  if (this._zoomLevel + dir > far) dir = -1;
  else if (this._zoomLevel + dir < near) dir = 1;
  this._periodicDirection = dir;
  this._setZoomLevel((this._zoomLevel + dir) as ZoomLevel);
  this._apply(fromWidth);
}

resetToDefault() (the “Now” button) gains one line — this._periodicDirection = 1 — so a resumed cycle always heads outward from default_zoom. The flip rule is self-correcting: whatever _zoomLevel is when the tick fires (a config edit moved it, the user left it mid-ladder before Home), the next move is always exactly ±1 rung from where the view actually sits.

B. Stateless triangle wave from a step counter

No direction field. Keep _periodicStep, increment it each tick, and map it through a triangle wave of period 2·(far−near) to get the level. resetToDefault() zeroes the counter. 

const span = far - near, phase = this._periodicStep++ % (2 * span);
const level = near + (phase <= span ? phase : 2 * span - phase);

Cleaner in the abstract — the turnaround is implicit, nothing to keep in sync. But the wave is computed from an internal counter that is blind to the actual _zoomLevel. configure() mutates _defaultZoomLevel live from the Lovelace editor; the next tick would then compute triangle(newNear, far, step) and jump the view several rungs in one tween — reintroducing the exact multi-rung lurch this issue removes.

A. The bug being fixed is a multi-rung jump. B’s counter can still produce one whenever anything else moves the zoom; A moves ±1 from the real current rung every time, by construction. The cost is one boolean-ish field and a one-line reset — cheap insurance against the failure mode we’re here to kill.

Design invariant preserved

The card still ships with the auto-cycle on (periodic_zoom_change default true), still steps one rung per 60 s refresh, still hands the camera back to the user on any zoom / drag and resumes only on “Now”. The zoom ladder (ZOOM_LEVELS = {1:800, 2:640, 3:480, 4:320}) and the MIN_ZOOM/MAX_ZOOM clamp in _setZoomLevel are untouched. The nav bar’s AU-per-orbit labels, visibility cone, and back/forward date buttons are unrelated and unchanged.
